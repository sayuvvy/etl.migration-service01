ItemReader rules as below
1. Cursor: lower memory, continuous DB connection, fewer round-trips; not great for long-running jobs or parallel consumers.
2. Paging: scalable, parallel-friendly; watch for inconsistent results if the table mutates mid-run—use snapshot/consistent reads if possible.
3. Idempotency: Always design processing to be idempotent; readers may re-deliver an item after restart.
4. Transaction Boundaries: Readers usually run outside of (or at the edge of) chunk transactions; ensure the data source read consistency matches your needs (e.g., transaction isolation).
5. Large Files: Use StaxEventItemReader or FlatFileItemReader with streaming—avoid loading the whole file.
6. Multi-threading: Many readers are not thread-safe; prefer one reader per partition/step execution, or use readers designed for concurrency (paging) and avoid sharing mutable state.
7. Validation & Skips: Add a ValidatingItemProcessor or custom processor; configure skip/retry policies at the Step level.

1. For CSV / fixed-width use FlatFileItemReader (+ MultiResourceItemReader if multiple files) with line tokenizer and fieldset line mapper
2. For XML use StaxEventItemReader
3. For JSON use JsonItemReader
4. For JDBC streaming use JdbcCursorItemReader
5. For JDBC scalable/parallel use JdbcPagingItemReader
6. For JPA/Hibernate use JpaPagingItemReader or Hibernate variants
7. For Spring Data repository use RepositoryItemReader
8. For MongoDB use MongoItemReader / MongoPagingItemReader
9. For JMS / AMQP use JmsItemReader / AmqpItemReader
10. For In-memory/testing use ListItemReader, IteratorItemReader, QueueItemReader
